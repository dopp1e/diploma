\chapter{IMPLEMENTATION}
\label{chap:implementation}
A completed trainer was implemented to provide the trainee with a high quality of a learning experience and a realistic environment.
The following chapter describes the process of creating the trainer.

\section{3D models creation (Hubert Leszczyński)}
\label{chap:models}

Most of the classes (Section \ref{sec:classes}) required the creation of appropriate 3D models for their objects.
The computer component models were created based on their real counterparts.
The first step was measuring their dimensions along all three axes.
Then, the prototypes were created in Blender as static mesh objects, composed of multiple polygons.
Additionally, every prototype was refined by beveling and by applying appropriate materials and modifiers.
Figure \ref{fig:ModelExample} presents an example model of a computer component, in this case a cooling system.

\begin{figure}[H]
	\centering
		\includegraphics[width=0.7\textwidth]{Images/3dmodel.png}
	\caption{Computer component model}
	\label{fig:ModelExample}
\end{figure}

Once the modeling phase was finished, the objects were exported to the Graphics Library Transmission Binary (GLB) format.
According to Pokorn{\'y}, "Blender's importer/exporter supports the following .glb/.gltf features: mesh objects, simple materials and shadeless textures [...]. Export options contain properties like merge vertices, pack images, shading type" \cite{10.1007/978-3-030-77442-4_35}.
These Blender functionalities allowed the models to be exported without losing their quality.
After exporting the 3D models to this format, they were ready to be integrated into the project.
Since UE5 provides native support for the GLB format, the models could be imported as assets.
This process required combining every static mesh into one object, and disabling Nanite support.
Nanite's virtual geometry system optimizes rendering by managing geometry \cite{NaniteDocumentation}, but this process negatively affected textures' details, most notably, the font legibility.
This was a significant issue, as the text printed on the computer components is crucial for their representation and identification.

\section{Object spawners (Hubert Leszczyński)}
\label{chap:spawners}

Having multiple objects, positions of which can change during application runtime, may sometimes cause them to get lost or move beyond the trainee's virtual hands range.
To address this issue, each holdable object can be dynamically generated by an object spawner.
Figure \ref{fig:SpawnObject} presents the blueprint for the function responsible for object generation.
The key parameter of the function is a reference to the subclass of HoldableComponent class (\ref{fig:HoldableObjectAbstraction}).
This reference allows the spawner to create an object of a specific type at its own location.

\begin{figure}[H]
	\centering
		\includegraphics[width=0.6\textwidth]{Images/SpawnObjectlOGIC.png}
	\caption{Blueprint illustrating the logic of a new object creation.}
	\label{fig:SpawnObject}
\end{figure}

The second function (Figure \ref{fig:SpawnObjectConditions}) determines whether the conditions of an object generation are met.
During each tick, the spawner calculates its distance from the previously generated object.
If the distance exceeds a configured threshold value, the spawner's timer variable begins incrementing.
Alternatively, if the object remains within the range limit, the timer is set to zero and it stops accumulating.
A new object can spawn only if the tracked object remains beyond the threshold distance for more than ten seconds.

\begin{figure}[H]
	\centering
		\includegraphics[width=0.7\textwidth]{Images/ObjectSpawningConditions.png}
	\caption{Blueprint illustrating the logic of checking the conditions for new object generation.}
	\label{fig:SpawnObjectConditions}
\end{figure}

The spawner mechanism ensures that the trainee always has access to the holdable objects, even if they were misplaced or lost during application runtime.

\section{Game object configuration (Hubert Leszczyński)}
\label{chap:objectConfig}

To increase the realism of the application, it was first necessary to correctly configure the physics and collision settings of the game objects.
As most of the game objects were created as static meshes, they are treated by UE as rigid bodies.
According to Millington, "Rigid-body engines treat objects as a whole and work out the way they move and rotate" \cite{MILLINGTON20071}.
This functionality significantly simplified the process of physics setup, as it allowed UE5 to automatically perform most of the calculations.
The gravity applied to the objects was adjusted to approximate Earth-like gravity, providing natural motion.
To achieve is effect, it was required to assign the global project settings using built-in UE5 unit system \cite{UnitSystem}.
The key parameter was Default Gravity Z \cite{PhysicsSettings}, which had to be set to -980 \,\text{cm}/\text{s}\textsuperscript{2} along the negative Z-axis to ensure a proper gravitational acceleration.

To appropriately set up the collision parameters, it was required to define new collision objects in the project settings for hands, slots and holdable objects.
Next, it was necessary to create a custom collision preset for each blueprint in the UE editor.
The methods of handling the collisions had to be properly assigned depending on the role of the objects to provide their appropriate interactions with each other.
Figure \ref{fig:CollisionSetup} presents the collision configuration for the computer component's mesh.

\begin{figure}[H]
	\centering
		\includegraphics[width=0.6\textwidth]{Images/CollisionSetup.png}
	\caption{Computer component collision configuration}
	\label{fig:CollisionSetup}
\end{figure}

The completed physics and collision configuration allows objects to fall freely and stop upon hitting predefined surfaces.
To simplify the learning experience, some objects were intentionally allowed to overlap with each other, for example computer components with the virtual hands.

Real-world computer components differ in their structure and socket arrangement.
To provide the trainee with more realistic experience, the computer component objects had to be configured to reflect these differences.
A key part of this process was placing the component slots directly on the meshes of the computer parts.
The position, scale and rotation of each slot were then manually adjusted to match the compatible components.
Additionally, each slot had to be configured with proper enumeration values to address the compatibility constraints.
A bright red material was then applied to the slots to improve their visibility.
Figure \ref{fig:ComponentConfiguration} presents a full configuration of a computer component, in this case a motherboard.

\section{Game scene design (Hubert Leszczyński)}
\label{chap:sceneDesign}

After completing the creation of 3D models and the game object configuration, the game scene was ready for design.
The game field was scaled to match the physical dimensions of the CAVE and surrounded by four walls, a floor and a ceiling.
Every element of the background was properly configured to provide the necessary collisions, preventing objects from accidentally leaving the scene.
The walls, floor and ceiling were decorated using freely available materials to make the scene resemble a real-world room.
Additionally, the room was enlarged to reduce the perceived claustrophobia of the environment.

Another essential set of objects placed in the game scene were the necessary pieces of furniture: four shelves and a desk acting as a workspace for the trainee.
To ensure order, the shelves were filled with object spawners, sorted by the type of component they generate.
Due to the large size of the computer case objects, they had to be placed under the desk.
To improve the realism of the workstation, the desk was decorated with the models of a monitor, keyboard and mouse.
The furniture orientation was adjusted to the CAVE, placing the desk against the front wall and the shelves against the side walls.

To ensure greater visibility of the game objects, a system of multiple point lights was installed throughout the scene.
The main light source was placed under the virtual ceiling to illuminate the entire room.
However, this placement caused computer components on the shelves to become less visible, due to the shadows cast by the furniture.
To address this issue, additional light sources were installed on each shelf.
Figure \ref{fig:LightSetup} presents the complete light configuration of the shelves.
After these updates, each object placed in the game scene was evenly and well lit, which improved the visibility of all components.

\begin{figure}[H]
	\centering
		\includegraphics[width=0.7\textwidth]{Images/LightSetup.png}
	\caption{Setup of the shelves light}
	\label{fig:LightSetup}
\end{figure}

Some of the objects in the scene were designed to provide a visual support for a trainee.
To ensure that less experienced trainees would not get lost when surrounded by a large amount of components of various types, every shelf was labeled with the type of component it contains.
A digital clock object was also placed above the desk to display the time elapsed during the virtual computer assembly process.
Additionally, the objective log was created as a 2D (two-dimensional) plane on one of the room's walls, providing step-by-step guidance and ensuring that the trainee can efficiently follow the assembly process.

To provide intuitive division between a virtual space and the real, physical CAVE, these two spaces were separated using glowing purple elements.
The chosen color ensured high contrast with the rest of the elements, making the boundary clearly visible from any position.
The material used to create these elements was configured to be emissive and translucent so they do not affect the stage lighting system.
This division was required to help the trainee distinguish the virtual walls from the CAVE screens, avoiding potential collisions with the physical CAVE walls.

\section{Tracking progress (Jakub Kinder)}
\label{chap:buildmanager}

The player's progress is tracked by a system called BuildManager, which is a specialized Quest Manager based on a tutorial by Ryan Laley \cite{laley_making_2023}.
Initially, progress tracking for individual PC components was considered for its development, however, unconstrained interaction with them made it difficult for given time constraints of the project, so global tracking approach was utilized instead.
Nonetheless, the core architecture of the system remained mostly unchanged, and the manager consists of 4 main parts:

\begin{itemize}
	\item 2 structures that define quests and their goals presented on figures \ref{fig:fgoalpic} and \ref{fig:fquestpic}.
	\item A persistent actor on the scene, bearing the same name as the system, that serves as the central state controller responsible for both communication with other objects and all progress tracking functionality.
	\item A data table containing quests and their goals
\end{itemize}

\subsubsection{Structures used in the tracking system}
Figure \ref{fig:fgoalpic} presents the FGoal structure, which defines a goal of a quest.
It consists of a goal description, that is to be displayed for the player, enumeration value Type which is used to identify goal as well as a boolean value IsOptional that signals whether certain goal is optional.
The core fields for the system's operation during runtime are integer fields, TargetCount and CurrentCount.
TargetCount defines threshold value that must be met for the goal to be completed, like number of components that need to be attached, while CurrentCount holds the current state value, which is updated reactively upon met conditions, defined by the system, for example number of RAM modules installed.

Another important structure is FQuest, presented on figure \ref{fig:fquestpic}, which is far simpler in construction than FGoal.
It defines a quest in the tracking system, and consists of an array of FGoal structures symbolizing goals needed to complete the quest.
Apart from that, it possesses description field, a text displayed to the player, and ID which is used to identify particular FQuest instance, mainly for communication with component objects or GUI element displaying current game state.

\subsubsection{Quest Data storage}
Both of the aforementioned structures were used to create UE5 Data Table, named QuestTemplate, with purpose of housing quest templates for ease of modifying existing ones or creating brand-new quests.
This approach provides other benefits - it simplifies the process of creating FQuest instances during runtime as well as ensures desired order of elements in FGoal array each time a template is copied.
However, at the current stage of the developed application the data table holds only one quest, whose goals are individual steps of PC assembly explained in \autoref{sec:pcassembly}.

\subsubsection{BuildManager actor}
The core functional component of the progress tracking system is the actor on the scene, named BuildManager.
It possesses 3 critical fields, Quest, containing a FQuest instance of currently executed by the user quest, QuestDataTable, which is a reference to mentioned above data table, and QuestLog, an instance of class BP\_QuestLog, that handles GUI element displaying current state of the quest to the player.

At the start of the game BuildManager, creates an FQuest instance, by copying a template the data table and awaits signals from PC component connection events.
Unlike most objects in the application, this manager does not utilize built-in event system as it is based on one dispatcher many listeners model.
Instead, the connection events search for an actor of BuildManager class and call its SaveProgress function with appropriate parameters, GoalType, enumaration value describing type of goal, and ProgressValue indicating progress made as an integer value.

\begin{figure}[!ht]
	\centering
	\includegraphics[width=0.75\textwidth]{Images/bmfindgoal.png}
	\caption{Piece of FindGoal function blueprint}
	\label{fig:bmfindgoal}
\end{figure}

After SaveProgress is called, first it executes FindGoal function, whose piece is presented on figure \ref{fig:bmfindgoal}, with Quest's goal array and GoalType given in its parameters.
The function then proceeds to iterate over the elements of the goal array using ForEach loop and checking if any of its elements is of requested type, then the function returns a copy of found goal with its index or null reference and index -1, depending on whether such goal exists or not.

\begin{figure}[!ht]
	\centering
	\includegraphics[width=0.8\textwidth]{Images/bmsaveprogress.png}
	\caption{Piece of SaveProgress function blueprint}
	\label{fig:bmsaveprogress}
\end{figure}

Next, the SaveProgress function, either ends execution or continues with valid FGoal instance and calls UpdateGoal function.
This updates goal's CurrentCount field increasing it by ProgressValue, then proceeds to check if CurrentCount >= TargetCount and sets the result to IsCompleted field of the structure and returns it. 
Afterward, SaveProgress saves the result back into the FGoal array of the quest, which is presented on figure \ref{fig:bmsaveprogress}.

Furthermore, this function also calls UpdatePRogress function that belongs to instance referenced in the QuestLog field.
This final call notifies the GUI handler object of a change in state and provides necessary data - the Quest's ID, the updated goal's index, and the ProgressValue - so that the GUI can be updated to provide the user with immediate and accurate feedback on their assembly progress.
