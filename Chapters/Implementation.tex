\chapter{IMPLEMENTATION}
\label{chap:implementation}
A completed trainer was implemented to provide the trainee with a high quality of a learning experience and a realistic environment.
The following chapter describes the process of creating the trainer.

\section{Environment setup (Jakub Jędrzejczyk)}

The implementation of the project was carried out using version 5.5.4 of Unreal Engine. The base for the project is the First Person game template, available in the Unreal Engine Editor.

	\caption{Selected preset in the Unreal Engine menu.}
	\label{fig:projectCreation}
\end{figure}

This preset was chosen because it provides a basic character first person perspective controller. While this controller will not be used in the final product, due to the nature of the CAVE environment, it allows for easy testing of the project in a non-VR environment.

\begin{figure}[H]
	\centering

	\caption{Starting point of the project - First Person template, from first person perspective.}
	\label{fig:FPSProjectPOV}

For the purposes of the project, the default environment was cleared out, leaving only the plane and walls. This provides much more space than is necessary for the CAVE environment, which is a cube with 3.4m sides. This space however allows for much easier testing of the project in a non-VR environment, as the player can move around freely. Throughout the many applications that we have been shown in the CAVE, many applications used rooms exactly the size of the CAVE room, which has at times felt claustrophobic. While it is not something being researched, we also wish to see if this will provide a more comfortable experience.

\begin{figure}[H]
	\centering
		\includegraphics[width=0.8\textwidth]{Images/ProjectEnvironment.png}
	\caption{Starting point of the project - First Person template, with cleared environment.}
	\label{fig:ProjectEnvironment}
\end{figure}

The next step was to set up the project to be ready for CAVE. Our consultant provided us with a plugin and a preset for it to be used with the tracking system used within the CAVE, called DTrack \cite{DTRACK}. We were also given a few Unreal Engine blueprint files that, when added to the project, allowed it to communicate with the tracking system. They were added to the project and set up so that there would be two hand objects, one for each hand controller. This functionality was tested using an application for desktop PCs we were provided with, which allows to move virtual controllers in 3D space, with their movement being sent to the Unreal Engine project.

\begin{figure}[H]

Here, the project's perspective is shown with two spheres representing the hand controllers in 3D space, each set to be in the opposite corner of the CAVE. These two objects in Unreal Engine are centered by default, but moving them in the software, visible on the right side of figure \ref{fig:ProjectWithTrackingTools} also moves them accordingly inside the software.

As an additional measure of ensuring adequate testing for non-CAVE environments, invisible walls were added, replicating the space of the CAVE. This way, the user can still move around freely in a non-VR environment, but will be limited to the size of the CAVE room.

\section{3D models (Hubert Leszczyński)}

Most of the classes (\ref{sec:classes}) required creating appropriate 3D models.
The computer component models were created based on their real counterparts.
The first step of creating each model of a computer component was measuring it's real dimensions in three axis.
Then, the prototypes of the models were designed in Blender as static mesh objects, which are composed of vertices, faces and edges forming a geometric shapes \cite{10.1007/978-3-030-77442-4_35}.
The prototypes were then subjected to the necessary modifications, and finally the appropriate materials were applied to them.
After finishing the work with designing the 3D models, they were exported to the GLB (Graphics Library Transmission Binary) format.
Figure \ref{fig:ModelExample} presents an example model of a computer component, in this case a cooling system.

\section{Dynamic object generation (Hubert Leszczyński)}

Having multiple objects, which position can change during an application runtime, may cause the trainee to encounter difficulties tracking them within the game scene.
To address that issue, each holdable object can be dynamically generated by an object spawner.
Figure \ref{fig:SpawnObject} presents the blueprint for the function responsible for object generation.
The most important parameter of the function is a reference to the subclass of HoldableComponent class (\ref{fig:HoldableComponentClasses}).
This reference allows the spawner to create an object of a specific type at the same position as the spawner.
\begin{figure}[H]
	\centering
		\includegraphics[width=0.7\textwidth]{Images/SpawnObjectlOGIC.png}
	\caption{Dynamic object creation logic}
	\label{fig:SpawnObject}
\end{figure}

The second function (figure \ref{fig:SpawnObjectConditions}) determines if the conditions of the object generation are met.
During each tick, the spawner is calculating the position from the previously generated object.
If the distance exceeds a fixed value defined separately for each spawner in the game scene for the certain amount of time, a new object will be created in the scene. 
\begin{figure}[H]
	\centering
		\includegraphics[width=0.7\textwidth]{Images/ObjectSpawningConditions.png}
	\caption{Conditions for the new object to spawn}
	\label{fig:SpawnObjectConditions}
\end{figure}

\section{Game object configuration (Hubert Leszczyński)}

To increase the realism of the application, it was first necessary to correctly configure the physics and collision settings of the game objects.
As most of the game objects were created as a static meshes, they are treated by UE as rigid bodies, so the physics engine considers them as a whole and determines how they move and rotate \cite{MILLINGTON20071}.
The most important aspect of objects physics configuration was properly setting up how they are affected by gravity.
To appropriately set up the collision parameters, it was required to define new collision objects in the project settings for hands and holdable objects.
Next, it was necessary to create a custom collision preset for each blueprint in the UE editor.
Figure \ref{fig:CollisionSetup} presents the collision configuration for the computer component's mesh.

\begin{figure}[H]
	\centering
		\includegraphics[width=0.6\textwidth]{Images/CollisionSetup.png}
	\caption{Computer component collision configuration}
	\label{fig:CollisionSetup}
\end{figure}

The completed physics and collision configuration allows objects to fall freely and stop their fall on predefined surfaces.
To simplify he gameplay, some of the objects were allowed to overlap with each other.

Real-world computer components differ from each other in their structure and socket arrangement.
To provide the trainee with a more realistic experience, the computer component classes had to be configured to reflect these differences.
The key element of this configuration was placing the component slots directly on the computer components objects.
The position, scale and rotation of each slot was then adjusted to match the fitting components.
Figure \ref{fig:ComponentConfiguration} presents a full configuration of a computer component, in this case a motherboard.
