\chapter{IMPLEMENTATION}
\label{chap:implementation}
A completed trainer was implemented to provide the trainee with a high quality of a learning experience and a realistic environment.
The following chapter describes the process of creating the trainer.

\section{3D models (Hubert Leszczyński)}

Most of the classes (\ref{sec:classes}) required creating appropriate 3D models.
The computer component models were created based on their real counterparts.
The first step of creating each model of a computer component was measuring it's real dimensions in three axis.
Then, the prototypes of the models were designed in Blender as static mesh objects, which are composed of vertices, faces and edges forming a geometric shapes \cite{10.1007/978-3-030-77442-4_35}.
The prototypes were then subjected to the necessary modifications, and finally the appropriate materials were applied to them.
After finishing the work with designing the 3D models, they were exported to the GLB (Graphics Library Transmission Binary) format.
Figure \ref{fig:ModelExample} presents an example model of a computer component, in this case a cooling system.

\section{Object loading (Jakub Jędrzejczyk)}

Thanks to the modular nature of the designed classes (\ref{sec:classes}), it was deemed possible to load the computer components into the scene at runtime, using a set of model files and descriptions in JSON \cite{brayRFC8259JavaScript2017} format.

For the purposes of preliminary feasibility testing, this functionality was implemented in a basic manner, not yet entirely representing the aforementioned classes.

This functionality is divided into two blueprints - the first one is responsible for scanning the folder with content in search of JSON files. Each folder in the UserContent directory is treated as a category for objects to be sorted into (GPU, CPU, etc.). Each one is then read, and an object is spawned in the scene, after which, a load function of the second blueprint is called on it, passing the contents of the JSON object and the category of the object.

\begin{figure}[H]
	\centering
		\includegraphics[width=1.0\textwidth]{Images/BasicLoadingBlueprint.png}
	\caption{Basic object loading blueprint}
	\label{fig:BasicLoadingBlueprint}
\end{figure}

The current loading scheme supports loading multiple meshes per object, which gives way to more complex models, such as GPUs with fans. Each mesh is expected to be a glTF 2.0 \cite{ISOIEC12113} model file, which is a modern format for 3D models, supporting PBR materials and animations. Each mesh can also be assigned a type, which is then used to assign specific functionality to it. For example, a mesh of type "Body" is treated as the main mesh of the object, while a mesh of type "Fan" could be rotated when the computer is turned on.

\section{Dynamic object generation (Hubert Leszczyński)}

Having multiple objects, which position can change during an application runtime, may cause the trainee to encounter difficulties tracking them within the game scene.
To address that issue, each holdable object can be dynamically generated by an object spawner.
Figure \ref{fig:SpawnObject} presents the blueprint for the function responsible for object generation.
The most important parameter of the function is a reference to the subclass of HoldableComponent class (\ref{fig:HoldableComponentClasses}).
This reference allows the spawner to create an object of a specific type at the same position as the spawner.
\begin{figure}[H]
	\centering
		\includegraphics[width=0.7\textwidth]{Images/SpawnObjectlOGIC.png}
	\caption{Dynamic object creation logic}
	\label{fig:SpawnObject}
\end{figure}

The second function (figure \ref{fig:SpawnObjectConditions}) determines if the conditions of the object generation are met.
During each tick, the spawner is calculating the position from the previously generated object.
If the distance exceeds a fixed value defined separately for each spawner in the game scene for the certain amount of time, a new object will be created in the scene.

\section{Game object configuration (Hubert Leszczyński)}

To increase the realism of the application, it was first necessary to correctly configure the physics and collision settings of the game objects.
As most of the game objects were created as a static meshes, they are treated by UE as rigid bodies, so the physics engine considers them as a whole and determines how they move and rotate \cite{MILLINGTON20071}.
The most important aspect of objects physics configuration was properly setting up how they are affected by gravity.
To appropriately set up the collision parameters, it was required to define new collision objects in the project settings for hands and holdable objects.
Next, it was necessary to create a custom collision preset for each blueprint in the UE editor.
Figure \ref{fig:CollisionSetup} presents the collision configuration for the computer component's mesh.

\begin{figure}[H]
	\centering
		\includegraphics[width=0.6\textwidth]{Images/CollisionSetup.png}
	\caption{Computer component collision configuration}
	\label{fig:CollisionSetup}
\end{figure}

The completed physics and collision configuration allows objects to fall freely and stop their fall on predefined surfaces.
To simplify he gameplay, some of the objects were allowed to overlap with each other.

Real-world computer components differ from each other in their structure and socket arrangement.
To provide the trainee with a more realistic experience, the computer component classes had to be configured to reflect these differences.
The key element of this configuration was placing the component slots directly on the computer components objects.
The position, scale and rotation of each slot was then adjusted to match the fitting components.
Figure \ref{fig:ComponentConfiguration} presents a full configuration of a computer component, in this case a motherboard.

\section{Game scene design (Hubert Leszczyński)}

After completing the creation of 3D models and the game object configuration, the game scene was ready for design.
The game field size was configured to match the dimensions of the CAVE, and then the background was created to reduce the perceived claustrophobia of the scene.
The walls, floor and ceiling were decorated using freely available materials to make the scene resemble a real-world room.
The main objects intalled inside the gamefield were four shelves for computer component spawners, and a desk providing a workspace for a trainee.
To ensure greater order, the spawners on the shelves were sorted by the type of the generated component.
There was also a digital clock object placed above the desk to indicate the time elapsed during the virtual computer assembly process.
The objective log was created as a 2D plane on one of the room's walls, so it can presented to the trainee in a simple manner.
To provide intuitive division between a game field and the background, they were separeted using glowing purple elements. 
To ensure grater visibility of the game objects, there was a a system of multiple point lights intstalled throughout the scene.

\section{Tracking progress (Jakub Kinder)}

The player's progress is tracked by a system called BuildManager, which is a specialized Quest Manager based on a tutorial by Ryan Laley \cite{laley_making_2023}.
The manager consists of 4 main parts:

\begin{itemize}
	\item 2 structures that define quests and their goals presented on figures \ref{fig:fgoalpic} and \ref{fig:fquestpic}.
	\item An actor on the scene that allows for communication between the tracking system and PC components.
	\item A data table containing quests and their goals
\end{itemize}


\begin{figure}[h!]%
	\centering
	\subfigure[]{
		\includegraphics[width=0.48\textwidth]{Images/FGoalParameters.png}
		\label{fig:fgoalpic}
	}%
	\hfil
	\subfigure[]{
		\includegraphics[width=0.48\textwidth]{Images/FQuestParameters.png}
		\label{fig:fquestpic}
	}
	\caption{Fgoal and FQuest structures used in BuildManager}
\end{figure}

Figure \ref{fig:fgoalpic} presents the FGoal structure, which defines a goal of a quest.
It consists of a goal description, that is to be displayed for the player, enumeration value Type which is used to identify goal as well as a boolean value IsOptional that signals whether certain goal is optional.
The core fields for the system's operation during runtime are integer fields, TargetCount and CurrentCount.
TargetCount defines threshold value that must be met for the goal to be completed, like number of components that need to be attached, while CurrentCount holds the current state value, which is updated reactively upon met conditions, defined by the system, for example number of RAM modules installed.

Another important structure is, presented on figure \ref{fig:fquestpic}, FQuest, which far simpler in construction than FGoal.
It defines a quest in the tracking system, and consists of array of FGoal structures symbolizing goals needed to complete the quest.
Apart from that, it possesses description field, a text displayed to the player, and ID which is used identify particular FQuest instance, mainly for communication with component objects or GUI element displaying current game state.
